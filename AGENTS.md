# Absolute Authority

`./CANON/*` is the only standing authority for governed work in this repository.

- If any habit, preference, prior pattern, or convenience conflicts with Canon, discard it immediately.
- If root guidance and Canon ever appear to diverge, interpret root guidance in the narrowest Canon-consistent way.
- Do not promote a local shortcut into standing repository law when Canon has not granted it.

## Non-Negotiable Execution Law

- Re-scan the relevant Canon surface before code generation, architectural guidance, contract edits, or package-law edits.
- Route repo-wide Canon revision, source absorption, reusable package maintenance, and owner-boundary work through `CANON/canon-compilation/**`.
- Do not silently blend multiple Canon owners into one improvised workflow.
- Do not claim readiness, safety, correctness, or completion without the proof shape required by the active Canon owner.

## Stop Conditions

- Stop and reroute if the governing owner is unclear.
- Stop and reroute if Canon is silent on a rule that would become reusable law.
- Stop and reroute if the proof path, promotion gate, or next owner is still implicit.

## Audit Rule

- Before concluding a session, self-audit the change against live Canon.
- Session-close reporting must name the larger workstream, the seam completed now, and the next seam to continue.

# Root Repository Contract

This repository owns the public concept, the Canon operating law, and the Canon-owned reusable package surfaces that downstream projects will copy.

## Root Scope

- The repository root defines the concept and the reusable operating law.
- `CANON/` is the primary source of truth for reusable operating law, reusable scaffold packaging, and downstream-copy behavior.
- Root documentation must describe the package-only scaffold model honestly and keep the purpose-first loop explicit.
- Repo-wide Canon maintenance, owner-boundary revision, source absorption, and reusable package maintenance route through `CANON/canon-compilation/**`.

## Purpose-First Rule

Every structure in this repository exists to help a downstream project perform `purpose.txt` as well as possible.

That means:

- plan quality matters only insofar as it improves purpose delivery
- implementation detail matters only insofar as it improves purpose delivery
- evaluation matters because it decides whether a change really helped the purpose
- release matters because the loop should eventually finish a useful application, not only iterate forever

## Repository Responsibilities

- keep the Canon-owned scaffold package usable as a control-plane plus `project/` worktree shell
- keep Canon routing broad, explicit, and reusable
- separate reusable scaffold package state from reusable Canon operating law
- avoid overstating automation that is not actually implemented
- keep reusable scaffold-source assets under `CANON/**` rather than depending on sibling explanation outside Canon
- keep deferred hardening explicit instead of claiming source-absorption closure means perfect finality
- keep orchestration and subagent-use rules inside Canon strongly enough that operators do not need scaffold prose to know when delegation is required
- keep repo-root guidance focused on concept ownership, package ownership, and Canon routing rather than duplicating owner-local procedure

## Canon Entry Rule

- Start from `CANON/README.md` when choosing the next Canon owner or skill.
- Treat `CANON/canon-compilation/**` as the owner for repo-wide Canon revision, reusable package edits, owner-map maintenance, source acquisition, and compilation work.
- Do not invent a sibling root scaffold authority when the Canon-owned package already defines the reusable shell.
- If a request spans multiple Canon owners, make the dominant next owner explicit and park the rest instead of blending responsibilities silently.

## Downstream Model

The copied scaffold should support:

1. define `purpose.txt`
2. generate `rubric.txt` once if absent
3. lock the rubric
4. route the next slice through design, planning, architecture, or direct execution as needed
5. run planner -> executor -> evaluator -> memory loops
6. promote only verified iterations
7. release when the application is ready enough

## Canon Packaging Rule

- Treat root `CANON/` as the reusable upstream source of truth for scaffold shipping.
- Treat `CANON/canon-compilation/packages/research-scaffold/` as the reusable shell package for downstream control-plane files.
- Do not rely on a sibling root scaffold directory for authority, parity, or operator guidance.
- Keep package-internal documentation topology-agnostic enough that the same package can be copied outward without becoming misleading.

## Reporting Rule

- Session-close reporting should state the larger workstream, the seam completed in the current session, and the next seam to continue.
- If Canon maintenance widened beyond the original seam, name the reroute trigger or parked follow-up explicitly.
